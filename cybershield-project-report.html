📌 1. Project Overview

CyberShield is a web-based cybersecurity monitoring dashboard built with Python and Streamlit. It provides security analysts and IT teams with a centralised, real-time view of user login activity, letting them quickly identify failed access attempts, unusual patterns, and potentially malicious IP addresses — all without needing a dedicated SIEM or external tooling.

The dashboard presents four high-level KPI metrics, a filterable login records table, two analytical charts, and a rule-based security alerts engine that categorises threats by risk level (High / Medium / Low). It is intentionally lightweight — built on plain Python logic with no machine-learning dependencies — making it easy to understand, extend, and deploy in any environment that runs Python.

✨ 2. Key Features

📊 KPI Metric Cards
Four at-a-glance counters: Total Logins, Successful Logins, Failed Logins, and live Suspicious Activities computed from the loaded dataset.
📋 Filterable Login Table
An interactive, colour-coded table of login records (timestamp, username, IP, result). A dropdown filter lets users view All, Success, or Failed entries instantly.
📈 Login Result Breakdown Chart
A bar chart comparing successful vs. failed login counts across the loaded dataset, giving an instant visual sense of the success/failure ratio.
🗺️ Failed Logins by IP Chart
A ranked bar chart highlighting which IP addresses generated the most failed attempts — the tallest bar is immediately actionable as a potential threat source.
🚨 Rule-Based Security Alerts
An automatic detection engine flags any IP that accumulates 3 or more failed logins. Alerts are sorted and colour-coded by risk level with detailed reason text.
🔴🟡🟢 Three-Tier Risk Scoring
Alerts are classified as High (≥10 failures), Medium (5–9), or Low (3–4), each with a distinct colour and explanatory rationale to guide triage decisions.
🎨 Dark-Theme UI
A GitHub-inspired dark colour scheme (#0d1117 background, #58a6ff accent) with fully custom CSS applied via Streamlit's markdown injection.
💾 Session-State Persistence
Loaded records are stored in Streamlit's session_state so the data and all derived views (charts, alerts, filters) persist across user interactions without re-fetching.

⚙️ 4. How It Works

1
Data Ingestion
The analyst clicks Generate Sample Data. The 20 pre-defined login records (timestamp, username, IP address, result) are written into st.session_state["records"], making them available to all downstream components for the rest of the session.
2
Failure Counting (Detection Engine)
A plain Python loop iterates over every record and increments a counter in a failed_per_ip dictionary for each failed login. This runs at the top of the script on every Streamlit rerun, so the counts always reflect the current session data.
3
Risk Classification
Each IP whose failure count reaches the alert threshold (≥ 3) is assigned a risk level via get_risk_level(): High (≥ 10), Medium (5–9), or Low (3–4). The resulting alert objects are sorted High → Medium → Low.
🔴 High — ≥ 10 failures 🟡 Medium — 5–9 failures 🟢 Low — 3–4 failures
4
KPI Metrics Display
Four st.metric() cards render Total Logins (1,482), Successful Logins (1,390), Failed Logins (72), and the live Suspicious Activities count (number of IPs that crossed the suspicious threshold of ≥ 5 failures).
5
Interactive Table & Filter
The login records are loaded into a pandas DataFrame and displayed via st.dataframe() with a Styler that colours the Result column green (Success) or red (Failed). A selectbox dropdown allows filtering by result type, with a live summary caption updating below the table.
6
Charts Rendering
Two st.bar_chart() visualisations are rendered side-by-side: the Login Result Breakdown (Success vs. Failed overall) and the Failed Logins by IP Address (ranked descending). Both charts are built from the unfiltered dataset to always show the full picture.
7
Security Alert Cards
Each flagged IP is rendered as a coloured alert card using inline HTML injected via st.markdown(). Cards display the IP, all usernames attempted, total failure count, risk level, and a plain-English explanation. A second selectbox lets the analyst filter alerts by risk level.

🚀 5. Future Scope

  • → Live data ingestion: Replace the static sample records with a real-time feed from system logs (e.g. /var/log/auth.log, Windows Event Log, or a syslog server) via file polling or a database connection.
  • → Machine-learning anomaly detection: Augment the rule-based engine with an ML model (e.g. Isolation Forest or time-series clustering) to surface behavioural anomalies that threshold rules would miss.
  • → IP geolocation & threat intelligence: Integrate an API such as ip-api.com or AbuseIPDB to enrich each alert with country-of-origin, ISP data, and prior abuse reports.
  • → Automated response actions: Add one-click buttons to block a suspicious IP via a firewall API (iptables, AWS Security Groups, etc.) or trigger a webhook to a ticketing system like Jira or PagerDuty.
  • → User behaviour analytics (UBA): Track per-user login patterns over time (normal hours, typical IP ranges) and alert when a login deviates from the established baseline.
  • → Historical trend charts: Add time-series line charts showing login volumes and failure rates over hours/days to help analysts spot attack campaigns that unfold slowly.
  • → Authentication & role-based access: Protect the dashboard itself with login credentials and restrict alert acknowledgement or block actions to authorised security personnel only.
  • → Export & reporting: Add a one-click CSV/PDF export of filtered records and alerts for incident documentation and compliance reporting.
